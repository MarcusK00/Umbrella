Umbrella · how it works

Umbrella, end to end

One MCP server per Umbraco site. The add-on inside the site knows which Umbraco products are installed and what the admin has switched off. The npm server on your machine asks it, loads only those products' tools into one process, and hands them to your AI tool under one set of names.

The whole system

Three parties, two machines. Only four kinds of request cross from your machine to the site, numbered on the arrows.

  1. Sign in. The server gets a token with the API user's client id and secret. Every later request carries it.
  2. Capabilities. The add-on answers with each product: installed, enabled, version, issues, and the dashboard's settings for it, resolved for the API user that asks.
  3. Catalogue. The server reports every tool group it loaded, stored per API user, so the dashboard can list groups to switch off.
  4. Tool calls. When the model calls forms--list-forms, the Forms tool code sends a normal request to the Forms Management API on the same site, with the same token.

One server instead of four

Each Umbraco product already publishes its own MCP server package (@umbraco-cms/mcp-dev, @umbraco-forms/mcp-dev, @umbraco-automate/mcp-dev, @umbraco-engage/mcp-dev). Umbrella does not run them as servers. It imports their ./collections entry point as a library and puts the tools into its own process.

  • You decide which servers to install, and keep that in step with the site yourself.
  • Tool names can collide: Forms and Automate both have get-server-info.
  • Nothing tells the model which server to use for "workflow".
  • Each product server also starts its own copy of the CMS MCP, so you get the CMS tools more than once.
  • The site decides which products load, through capabilities.
  • Every name gets a product prefix; a duplicate final name stops startup.
  • The server's instructions route the model to a product before it picks a tool.

Why the toolkit is needed

@umbraco-cms/mcp-server-sdk is the toolkit every product MCP is built on. All four product packages depend on it, so it is in node_modules either way. Umbrella declares it itself because it takes only the products' tools and does the server part on its own, with the same toolkit.

Why not run the product servers?

That is the setup Umbrella replaces. Each product MCP starts its own copy of the CMS MCP as a child process and passes its tools through as cms--*. With Forms and Automate as separate servers you get the CMS tools two or three times, several Node processes, several sign-ins, nothing that picks servers from what the site has, and name clashes such as get-server-info twice.

A proxy that starts the product servers as child processes and forwards their tools would also work, but the duplicate CMS copies come with it, every process signs in separately, and the dashboard settings would have to be turned into env vars for each child. Loading the collections into one process avoids that. In exchange, Umbrella provides what the product servers normally provide, using the toolkit.

Why exactly one copy

The toolkit keeps the API client provider (see When a tool is called) as module-level state: one global per loaded copy of the package. Umbrella calls configureApiClient on its copy. A product that resolved its own nested copy would call getApiClient() on a copy nobody configured, and every one of its tools would fail.

  • npm/package.json pins the toolkit to one exact version and forces it onto every product with overrides.
  • overrides only apply in the root project, so under npx one copy relies on every product package depending on a compatible version. Today they all resolve to the same one.
  • scripts/pack-check.sh installs the packed package the way users do and fails if a product's tools are missing.
  • At runtime, checkSingleSdk skips a product with its own nested copy and reports it in get-mcp-health, so it can't break the others.

Why declare it at all?

Umbrella imports from it directly, so it belongs in dependencies. Without that, the import only works while npm happens to place a product's copy at the top of node_modules, and there would be no exact pin for the overrides rule to point to.

What the add-on reports

The add-on takes no package dependency on any product. A detector is just a few names, checked against what the running site has loaded.

Startup, in order

All of this happens once, when the AI tool starts the server. The order matters: the server's instructions are fixed when it is created, so it can only be created after it knows which products loaded.

Which products load

selectModules() asks four questions per module. The first answer that decides wins, and the reason is kept for get-mcp-health.

Which tools survive

Each loaded module's tools pass the same gates, using the product's own unprefixed names. Environment variables live in the AI tool's config; site settings come from the dashboard via capabilities.

What the model sees

Before registering a tool, Umbrella renames it, labels its description with the product, and points any mention of a sibling tool at that tool's registered name.

When a tool is called

The shared toolkit has one process-wide API client provider, but Forms needs a Forms client and CMS a CMS client. Umbrella installs one provider that looks up the current product from an AsyncLocalStorage, and wraps every handler so the right product is set for the length of the call.

This only works if every product uses the same copy of the toolkit; Why the toolkit is needed explains why and how that is guarded.

The settings loop

The dashboard can only offer tool groups the server has told it about, and the server only reads the settings when it starts. So a change goes round once.

Settings per API user

A team on one site usually has one API user per developer. The tool settings you save without picking a user are defaults for all API users. An admin can override a product for one user, and each user's catalogue is stored on its own. The server doesn't change: the site works out which settings belong to the caller.

  • Override per product, all or nothing. An override holds the product's switched-off groups and its level (full, noDestructive or readOnly). A product without one follows the defaults, also when they change later.
  • Every API user is selectable, also one that has never connected. The user's own server picks the settings up on its next start.
  • Counts per user. The Tool groups counts come from the selected user's own report. A user without one sees the most recent other report, with a note. Forgetting a connection in the Overview clears that user's report and keeps its overrides.
  • Still guardrails. The npm server applies them on each developer's machine; the API user's Umbraco permissions are the real boundary.
